# FRAME ATLAS v5.40 — PRO PHOTO LOCATION SCOUT

개인용 사진촬영 로케이션 스카우팅 프로그램입니다. `index.html`과 `data/places.js` 외에 `data/review-workflow.js`가 위치·사진·허가·현장 기술 검증 기록의 입력·저장·내보내기를 담당합니다.

## 핵심 기능 및 검증 원칙
- 장소 레코드 수는 계속 변경되므로 현재 수량은 `tools/validate.py` 실행 결과와 `tools/report.md`를 기준으로 확인합니다.
- 장소 상세 화면에 **검증 워크스페이스**를 추가해 실제 주소·정밀 좌표·진입점·답사일, 사진 일치·출처·이용권, 상업촬영 허가 근거·확인일을 직접 기록할 수 있습니다.
- 정밀 좌표로 승인 저장하려면 한국 범위의 위도·경도, 출처 URL, 확인일이 필요합니다. 승인 또는 허가 불필요로 기록할 때는 공식/서면 근거 URL과 확인일이 필요합니다.
- 현장 실측 촬영 포인트 3개와 빛·장비 반입·전력·주차·대기공간·안전·날씨 대안을 별도 기록합니다. 기존 촬영 포인트 설명은 현장 실측을 뜻하지 않습니다.
- 품질 대시보드에서 자료 완성도, 기획상 창작/제작 적합도, 현장 준비도, 검증 신뢰도를 분리해 확인하고 현황 CSV를 내려받을 수 있습니다.
- 사용자 검증 기록은 `faReview57_<ID>` 키로 기기 저장되며 JSON 백업 및 GitHub 백업·동기화 대상에 포함됩니다.
- PWA 서비스 워커가 앱 셸, 장소 데이터, 검증 워크플로 파일을 same-origin 캐시합니다. 외부 이미지·지도·검색 API는 오프라인 보장 대상이 아니며 온라인 첫 실행이 필요합니다.

## 실행 및 배포
1. 앱은 저장소 루트의 `index.html`을 기준으로 열립니다. GitHub Pages 주소는 `https://casio8000.github.io/FRAME_ATLAS/`입니다. 브라우저의 로컬 파일 정책에 따라 일부 기능(서비스 워커, 외부 요청)이 제한될 수 있습니다. 완전한 PWA/오프라인 테스트는 GitHub Pages 또는 localhost 같은 HTTP(S)에서 진행하세요.
2. 이 저장소는 이미 `index.html`, `data/`, `assets/`, `sw.js`가 루트 기준으로 구성되어 있습니다. 추가 배포 시 하위 폴더가 한 겹 더 생기지 않도록 주의하세요.
3. 업데이트 전에 앱의 DB 백업/복원 메뉴에서 사진·메모·후보·촬영 건을 백업하세요. 검증 기록도 백업 파일 및 GitHub 백업 키에 포함됩니다.
4. 저장소 루트에서 `python tools/validate.py` 와 `python tools/check_app.py` 를 실행합니다. GitHub Actions에서도 push/PR마다 자동 점검하며, 검증 경고는 데이터 결함 가능성 또는 현장 확인 공백을 나타냅니다.

## v5.38 백업 항목별 병합
- 백업 복원의 **병합 복원**은 겹치는 LocalStorage JSON 데이터와 장소 레코드를 항목별로 병합합니다. 백업에만 있는 값은 추가하고, 같은 필드를 양쪽에서 다르게 수정한 경우 현재 기기의 값을 우선 보존하며 충돌 수를 보고합니다.
- 배열은 중복을 줄이도록 합치며, ID가 있는 배열의 객체는 객체 필드 단위로 병합합니다.
- 사진은 기존 메타데이터를 무조건 덮어쓰지 않고 비교합니다. 같은 사진 데이터가 다르면 현재 기기의 사진을 유지하고 충돌로 집계합니다. 실제 사진 파일 데이터가 백업에 없으면 불완전한 사진 항목을 가져오지 않습니다.
- 전체 덮어쓰기는 계속 별도 선택지로 남아 있으며, 선택 시 확인 메시지가 표시됩니다.
- GitHub Actions에서 node tools/test_backup_merge.js로 병합 규칙을 자동 테스트합니다.
- 제한: 이 단계는 **파일을 직접 불러와 병합할 때** 적용됩니다. 병합은 삭제를 다른 백업에 전파하지 않으므로 삭제한 항목이 다른 백업에서 다시 추가될 수 있습니다. PC와 아이폰 사이 자동 원격 업로드/다운로드, 삭제 표식, 오프라인 대기열, 동시 편집의 원격 충돌 해결 UI는 아직 구현되지 않았습니다.

## 공용 데이터·사진 동기화 구조
현재 개인 기록은 기기별 저장소에 캐시되므로, 양방향 자동 동기화 엔진과 비공개 사용자 데이터 저장소로의 단계적 전환이 필요합니다. 현재 공유 스냅샷을 더 자주 업로드하는 것만으로는 충돌과 덮어쓰기 문제를 해결할 수 없습니다. 설계 및 단계별 전환 계획은 `SYNC_ARCHITECTURE_PROPOSAL.md`를 참고하세요.


## v5.39 기기별 안전 동기화 (단계적 도입)

- GitHub 백업·동기화 화면에 별도의 **안전 동기화** 경로를 추가했습니다. 기존 기기 데이터는 LocalStorage/IndexedDB에 남고, 원격에는 기기별 레코드·사진 파일·manifest를 분리해 저장합니다.
- 동기화 시작 전에 사진 포함 전체 백업 다운로드를 요구하고, 다시 시작을 눌러 사용자가 확인한 경우에만 동기화를 활성화합니다. 앱은 원격 저장소가 **비공개(private)** 인지 확인하며 공개 저장소에는 안전 동기화 데이터를 올리지 않습니다.
- 변경된 항목을 기기별 경로에 기록하고, 다른 기기의 새 레코드를 기존 데이터와 병합합니다. 동일 필드 충돌은 현재 기기 값을 우선 보존하고 충돌 내역 보기에서 확인할 수 있습니다. 오래된 원격 데이터가 삭제 기록을 자동으로 되살리지 않도록 삭제 시각을 비교하며 불확실한 삭제 충돌은 자동 삭제하지 않습니다.
- 사진 Blob은 전체 JSON에 끼워 넣는 대신 파일로 저장합니다. GitHub API 업로드 안정성을 위해 개별 사진 650KB, JSON/manifest 750KB 한도를 둡니다. 제한을 넘겨 업로드가 실패해도 기기의 원본 파일은 삭제하지 않습니다.
- 앱 시작·화면 복귀·온라인 복귀 및 변경 후 재시도를 통해 동기화를 시도합니다. 동기화 도중 변경이 더 발생하면 후속 실행을 대기합니다.
- **설정은 PC와 아이폰 각각에서 수행해야 합니다.** 같은 비공개 저장소/토큰을 설정하고 두 기기에서 안전 동기화를 활성화해야 합니다. 첫 연결 시 양쪽 기기의 현재 데이터가 서로 다르면 항목 병합/충돌이 생길 수 있으므로, 각 기기의 자체 백업을 별도 보관하세요.
- 주의: GitHub 토큰은 브라우저 저장소에 남습니다. 저장소 하나로 제한한 Fine-grained 토큰을 사용하고, 다른 사이트/기기와 공유하지 마세요. 이 단계의 실제 PC·iPhone 연결 검증은 사용자 비공개 저장소의 설정과 토큰이 필요하므로 자동 테스트만으로 완료를 선언할 수 없습니다.


## v5.40 동기화 재시도 안정화

- 일시적 네트워크 실패, GitHub의 408/409/425/429/5xx 응답 및 rate-limit 응답에 대해 제한된 자동 재시도를 추가했습니다.
- 재시도 대기 간격은 5초 → 15초 → 30초 → 60초 → 120초이며, 최대 5회 시도 후 자동 재시도를 멈춥니다.
- 401/일반 403 권한 오류와 SHA 기반 동시 수정 충돌(409/422)은 자동 반복하지 않습니다. 충돌 오류는 최신 원격 상태를 다시 확인한 뒤 사용자가 재시도하도록 해 맹목적인 덮어쓰기를 피합니다.
- 동기화 비활성화 시 재시도 타이머를 정리하고, 성공하면 재시도 횟수를 초기화합니다.
- `tools/test_device_sync.js`에 오류 분류와 대기 간격 테스트를 추가하고 `tools/check_app.py`에서 회귀 방지 정적 검사를 수행합니다.
- 범위: 이는 일시 오류 대응 보강입니다. 사용자 비공개 저장소와 PC·iPhone의 실제 왕복 동기화, 사진 대용량 및 오프라인 복구는 별도 실기 검증이 필요합니다.
